# 1.0.2 发布说明（PotPlayer 播放中反复「缓冲」排查与中转稳健性修复）

日期：2026-11-01

## 报障现象

- 用 PotPlayer 播放（Rust 中转 → 本机 FLV）时，播放中途会突然出现 PotPlayer 自带的「缓冲: XX%」，并反复出现；同一时段用 mpv 没有同等明显的感知。

## 现场证据（2026-11-01 20:36–21:06，真实虎牙房间，全程只读观测，未打断用户播放）

- 用户播放连接 #3 全程单条上游响应、无重连：20:50:30–21:06 稳定 103.2 tag/s（视频 60.0 + 音频 43.1）、媒体时间/墙钟 = 1.0002x；说明中转稳态不丢帧、不欠实时。
- 20:44:58–20:50:25 上游出现间歇慢段：用户连接平均 0.77x、最低 21 tag/s；同期新增的独立只读 tap（只读、无播放器反压）也只有 0.22–0.37x ⇒ 慢段来自共享的上游网络路径（本机虎牙流量经 Clash TUN 代理），不是中转写入反压。
- 慢段结束、上游追上直播边缘时，**同一条 HTTP 响应内**出现 +114,517 ms 的音视频同步时间戳跳变（tap seq 5234→5235；到达间隔仅 0.52 s，后接 112 KB 关键帧；relay 无重连、无 segment ended）——1.0.1 会把该跳变原样转给播放器，播放器据此重建分离器缓存，出现第二次「缓冲」。
- PotPlayer 的读缓存很小（报障截图 00:03:21 / 00:03:23，约 2 s 余量）：上游一慢就欠载，这是「缓冲: XX%」的直接原因；该版本（26.10.21）没有可编程的网络缓冲/读取超时设置（本机注册表全量与 DLL 字符串检索确认）。
- 直连 CDN 复核仍是分段行为：每次响应 0.28–0.41 s 内吐 0.93–3.40 MB 后 EOF，会话间内容重叠；同一 URL 约 40 s 后用废（与 `docs/decisions` 记录的历史虎牙行为一致）。

## 本版改动

1. **中转写超时 5 s → 15 s**（对齐旧版启动器的发送超时）：播放器因自建缓存暂停读取超过 5 s 时，不再被立即判为写失败、断开整条连接并重建上游。
2. **同一响应内大时间戳跳变重基**：音视频共用一条修正，跳变后从已转发时钟 +20 ms 连续续接（被上游跳过的内容仍然丢失，但播放器时钟不断裂、不把它当成流重启）；`relay.log` 记 WARN，`GET /__livehub/status` 新增 `timeline_jumps` 计数便于以后复现观察。
3. **正常媒体分段结束后的重连等待 1 s → 150 ms**：CDN 轮换短响应时缩短播放器无数据窗口；重连重叠去重逻辑不变。
4. 文档更新：`docs/relay-playback.md` 的中转/播放生命周期与状态字段。

## 验证

- 离线：`cargo check --locked --offline`（默认 GUI 与 `--no-default-features`）；`flv::tests` 14/14（新增 2 个时间戳重基单测）；relay/reconnect/playback 契约测试通过（数字见 `docs/validation.md` 的 1.0.2 小节）。
- 运行态（只读，不打断用户播放）：健康时段两只独立 tap 合计 440 s，>1 s 到达空档 0 次；1.0.1 会话 20:50:30–21:06 媒体/墙钟 1.0002x。播放器模型（读缓存 2 s，PotPlayer 形状）与 15 s 模型在 480 s 健康时段均 0 次欠载。
- **未验证**：本版没有在用户真实 PotPlayer 会话上做 A/B（用户正在观看，未重启）；`timeline_jumps` 需要在下次慢段复现时观察；上游慢段若来自代理/运营商，程序侧无法提升带宽，只能缩短可恢复窗口。

## 已知限制与建议

- 上游持续慢于实时（本次约 5 分钟 0.22–0.37x）时，任何本地缓冲都无法避免播放器欠载；建议同时排查 Clash TUN/代理节点质量，或对该域名走直连后复测。
- PotPlayer 26.10.21 无公开可编程的缓冲/读取超时项，播放器侧只能靠「时移」等人工设置缓解，程序不擅自改用户播放器配置。
